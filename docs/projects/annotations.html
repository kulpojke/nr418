H3 Building-Damage Annotation Project

Project concept

Build a reproducible workflow that divides a disaster-affected area into H3 cells and lets people manually classify Overture building footprints using pre-event and post-event imagery.

H3 should be used to partition, assign, and track work. The annotation unit should remain the individual Overture building, identified by its Overture/GERS ID.

Area of interest
  -> extract Overture buildings
  -> assign each building to one H3 task cell
  -> annotator claims a cell
  -> inspect before/after imagery
  -> label each building
  -> review and export the results

This is a prototype version. It will be limited to one event and one area, with imagery selected in advance.

Core workflow

  1. Select an event, area of interest, and observation period.
  2. Extract building polygons from a pinned Overture release.
  3. Assign each building to exactly one H3 cell using a point guaranteed to lie inside its footprint. Do not assign a building to every cell its polygon touches.
  4. Count buildings per cell and select a resolution that produces manageable tasks.
  5. Present one claimed H3 cell, its buildings, and pre/post imagery to an annotator.
  6. Save each decision immediately and track task progress.
  7. Have multiple people annotate a subset of cells for quality assessment and adjudication.
  8. Export the annotations with enough provenance to reproduce and interpret them.

H3 resolutions 9 or 10 are reasonable starting points, but the final resolution should be chosen using the number of buildings per task rather than area alone. Resolution 9 averages about 0.105 km² per hexagon and resolution 10 about 0.015 km², although actual cell areas vary. See the H3 resolution statistics.

When a building crosses a hexagon boundary, assign it using a representative interior point but display a buffer around the active cell so the annotator retains visual context.

Annotation interface

The minimum useful interface should provide:

  • A queue of available H3 cells.
  • A way to claim, release, skip, and complete a cell.
  • Automatic zoom to the selected cell.
  • Synchronized pre-event and post-event imagery, preferably with a swipe or side-by-side control.
  • Clickable Overture footprints over the imagery.
  • Keyboard shortcuts for rapid classification.
  • A visible completed/remaining building count.
  • Undo and autosave.
  • An export mechanism and an administrative progress view.

Use more than a forced binary classification:

  • destroyed
  • not_destroyed
  • uncertain
  • not_visible
  • footprint_mismatch

An optional damage-level field could be added later, but only after students establish a clear interpretation guide with image examples.

Each annotation should record at least:

building_id
overture_release
h3_cell
label
confidence
annotator_id
imagery_source
pre_image_date
post_image_date
annotation_timestamp
notes

Labels should be described as observations made from specified imagery, not as authoritative structural-safety assessments.

Possible implementations

QGIS workflow

QGIS is the fastest path to a working prototype and may be preferable if the learning goal is GIS workflow design rather than web development.

The recommended QGIS version of the project is still a data pipeline plus an annotation project. Prepare the Overture and H3 layers outside QGIS first, then give students a QGIS project that already contains the task grid, building footprints, imagery, styling, and annotation fields.

1. Choose the building time period

.

Overture buildings should be selected by release, not by an arbitrary date range. A release is a snapshot such as 2026-06-17.0; it is not the date on which every building was originally mapped. For disaster annotation, pick and record the release that is the latest release available before 2022-07-22 .

Important constraints:

  • Do not use “latest” for a class project unless the exact release is recorded.
  • Overture public release buckets retain only the most recent releases for a limited time, so download and archive the subset used for the course.
  • If the event is historical and the matching release is no longer public, use an archived copy, a previously downloaded subset, or document that the available Overture release is a proxy for the desired building inventory.
  • Record the Overture release, schema version, download date, AOI, and query used to create the local file.

For a quick current-release extract, the Overture Python client can export buildings for a bounding box:

overturemaps download \
  --bbox=-120.15,35.20,-120.00,35.32 \
  -f geoparquet \
  --type=building \
  -o data/overture_buildings_latest.geoparquet

For a reproducible pinned release, prefer DuckDB so the release appears directly in the source path. Replace the release ID in the path with the release chosen for the project:

LOAD spatial;
LOAD httpfs;
SET s3_region = 'us-west-2';

COPY (
  SELECT
    id AS building_id,
    geometry
  FROM read_parquet(
    's3://overturemaps-us-west-2/release/2026-06-17.0/theme=buildings/type=building/*',
    filename = true,
    hive_partitioning = 1
  )
  WHERE
    bbox.xmin <= -120.00 AND bbox.xmax >= -120.15
    AND bbox.ymin <= 35.32 AND bbox.ymax >= 35.20
) TO 'data/overture_buildings_2026-06-17.gpkg'
WITH (FORMAT GDAL, DRIVER 'GPKG');

Use the bounding-box predicate first because it lets DuckDB skip remote Parquet chunks. If the AOI is not rectangular, run a second clip in QGIS or add a spatial intersection against an AOI polygon after the bounding-box filter.

2. Load Overture buildings into QGIS

Add the exported GeoPackage or GeoParquet file with Layer -> Add Layer -> Add Vector Layer, or drag it into the QGIS canvas. Set the project CRS to an appropriate local projected CRS for editing and measurement, but keep a WGS84 copy of the building layer available for H3 generation because H3 indexes use longitude/latitude.

Inspect the buildings before building the task grid:

  • Check whether the footprints line up with the pre-event imagery.
  • Remove or flag obvious duplicates only if the rule is documented.
  • Keep building_id unchanged; it is the stable identifier used in the annotation export.
  • Add fields for overture_release, h3_cell, label, confidence, annotator_id, imagery_source, pre_image_date, post_image_date, annotation_timestamp, and notes.

3. Assign buildings to H3 cells

The cleanest assignment rule is: one building gets one H3 cell, based on an interior representative point. Do not assign a building to every H3 cell that its footprint touches.

One reproducible Python script can create both the building assignment layer and the H3 task layer:

import geopandas as gpd
import h3
from shapely.geometry import Polygon

H3_RESOLUTION = 9
OVERTURE_RELEASE = "2026-06-17.0"

buildings = gpd.read_file("data/overture_buildings_2026-06-17.gpkg")
buildings = buildings.to_crs(4326)

points = buildings.geometry.representative_point()
buildings["h3_cell"] = [
    h3.latlng_to_cell(point.y, point.x, H3_RESOLUTION)
    for point in points
]
buildings["overture_release"] = OVERTURE_RELEASE

def h3_polygon(cell):
    boundary = h3.cell_to_boundary(cell)
    return Polygon([(lng, lat) for lat, lng in boundary])

counts = buildings.groupby("h3_cell").size().rename("building_count")
h3_cells = gpd.GeoDataFrame(
    {"h3_cell": counts.index, "building_count": counts.values},
    geometry=[h3_polygon(cell) for cell in counts.index],
    crs="EPSG:4326"
)

buildings.to_file("data/buildings_with_h3.gpkg", layer="buildings", driver="GPKG")
h3_cells.to_file(
    "data/buildings_with_h3.gpkg",
    layer="h3_tasks",
    driver="GPKG",
    mode="a"
)

Load both layers into QGIS from the GeoPackage. The buildings layer carries the h3_cell assignment for each footprint, and the h3_tasks layer gives QGIS real polygon geometries for the H3 cells. Style h3_tasks by building_count to confirm that task sizes are reasonable before annotation begins.

4. Alternative: create H3 directly inside QGIS

If students should practice more of the workflow in QGIS, install the H3 Toolkit plugin from Plugins -> Manage and Install Plugins. The plugin adds an H3 processing provider, but QGIS must also have the Python h3 package available.

Useful tools:

  • Create H3 grid inside polygons: generate H3 polygons for the AOI.
  • Create H3 grid: generate H3 polygons for the current map extent.
  • Count points on H3 Grid: convert building representative points into H3 polygons with counts.

The QGIS-only path is:

  1. Run Vector geometry -> Point on surface on the Overture building footprints.
  2. Run H3 -> Count points on H3 Grid on those representative points at resolution 9 or 10.
  3. Save the output as a GeoPackage layer named h3_tasks.
  4. Run Join attributes by location so each representative point receives the containing h3_tasks.index value.
  5. Join that point layer back to buildings by building_id, then rename or copy index to h3_cell.
  6. Verify that every building has exactly one h3_cell.

This is convenient for teaching, but the scripted Python path is easier to reproduce and audit.

5. Build the QGIS annotation project

Once buildings and H3 cells are prepared:

  • Add pre-event and post-event imagery as separate raster or XYZ/WMTS layers.
  • Put h3_tasks above imagery with transparent fill and a visible outline.
  • Put buildings above imagery with categorized symbology for label.
  • Use a layer filter such as "h3_cell" = '8929a1d75afffff' when an annotator is working on one task cell.
  • Add a rule-based style for unlabeled buildings so remaining work is obvious.
  • Configure the building layer’s attribute form with value maps for label and confidence.
  • Enable editing only on the annotation fields, not on building_id, h3_cell, or geometry.
  • Save the project with relative paths so the package can be moved between machines.

For single-user or small-class work, each student can receive a GeoPackage containing assigned H3 cells and their buildings. For simultaneous editing, store the same layers in PostGIS and add fields such as claimed_by, claimed_at, completed_at, and review_status to the h3_tasks table.

Advantages are rapid development, strong raster support, offline operation, and familiar editing tools. Weaknesses are distributing updates, preventing duplicate work, merging files, and supporting many simultaneous annotators. A shared PostGIS database can address concurrency but adds administration and makes the workflow less portable.

Google Earth Engine application

Earth Engine is attractive when appropriate pre/post imagery is already in its catalog or has been uploaded as assets.

  • Upload the AOI, H3 IDs, and an extracted Overture building subset as a table asset/FeatureCollection.
  • Build a JavaScript Earth Engine App with before/after maps and label buttons.
  • Use Earth Engine’s UI widgets to navigate cells and switch imagery.
  • Export completed annotations or send decisions to a separate external database/API.

Earth Engine Apps are easy to share and can be used without requiring every viewer to have an Earth Engine account. Earth Engine also provides map, button, panel, and drawing widgets through its UI API. Its main limitation for this project is persistent collaborative write-back: a separate backend is likely necessary for reliable multi-user task claiming and annotation storage. Large building collections should be uploaded as table assets rather than embedded directly in a script.

Standalone notebook

A Jupyter notebook is a good teaching prototype or single-annotator tool.

  • Query an AOI from Overture with DuckDB or the Overture client.
  • Compute a representative point and H3 ID for each building.
  • Display imagery and polygons using ipyleaflet, leafmap, or another interactive map widget.
  • Use ipywidgets buttons and keyboard controls to assign labels.
  • Save after every decision to SQLite, GeoPackage, or Parquet.

This implementation keeps the data pipeline visible and is straightforward to distribute as a reproducible environment. It is less suitable for many annotators because notebooks do not naturally provide task locking, authentication, centralized persistence, or robust deployment. It is an excellent first milestone before moving the same data model into a web application.

Imagery requirements and risks

Imagery is likely to be harder than either H3 indexing or Overture extraction.

  • Building-level assessment generally requires high-resolution aerial or satellite imagery; Sentinel-2 is usually too coarse for individual buildings.
  • Pre/post images must have documented acquisition dates and reasonable co-registration.
  • Clouds, smoke, shadows, seasonal differences, and oblique views need explicit handling.
  • Overture polygons may be stale, missing, duplicated, or offset from the imagery.
  • Imagery licensing must permit classroom display and the intended distribution of derived annotations.

For the first course offering, provide a prepared imagery catalog rather than requiring the tool to discover suitable imagery for arbitrary events. If imagery is delivered as COGs, a tile service can provide browser-friendly access without first creating a large static tile pyramid.

Quality assurance

  • Write a concise labeling manual with positive, negative, uncertain, obscured, and footprint-error examples.
  • Run a small pilot before opening the full AOI.
  • Double-annotate a sample of tasks and calculate inter-annotator agreement.
  • Include an adjudication workflow for disagreements.
  • Track skipped cells and missing imagery rather than treating them as complete.
  • Preserve original judgments as well as adjudicated labels.
  • Test performance in dense and sparse neighborhoods before fixing the H3 resolution.

Licensing and reproducibility

Record the exact Overture release because its data and schema change over time. Overture building data is distributed under ODbL and includes source-specific attribution requirements; consult the Overture buildings guide and attribution guidance before publishing a combined dataset.

The project should also record imagery providers, licenses, acquisition dates, processing steps, software versions, H3 resolution, AOI geometry, and label-schema version.

Suggested team responsibilities

  1. Data pipeline: Overture extraction, validation, H3 assignment, and task generation.
  2. Imagery: catalog preparation, tiling, dates, alignment, and attribution.
  3. Interface and database: map interaction, labels, task claiming, persistence, and export.
  4. QA and deployment: annotation guide, testing, adjudication, documentation, and hosting.

Recommended first milestone

Before building a multi-user application, require each team to demonstrate this complete vertical slice:

  1. Extract approximately 500–2,000 Overture buildings from a pilot AOI.
  2. Assign them uniquely to H3 cells.
  3. Load one pair of pre/post images.
  4. Navigate to a selected H3 cell.
  5. Label and persist at least 25 buildings.
  6. Export records containing full building, imagery, task, and annotation provenance.

Once that works reliably, students can add collaboration, task locking, QA, dashboards, and broader imagery support.
